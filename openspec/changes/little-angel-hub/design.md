## Context

See proposal.md - Why for motivation. Key existing structure this builds on:

1. **`buildTree()` (`lib/utils/buildTree.ts`) already does almost everything needed**, but is hardcoded to read `student.introducer`. It builds a forest (multiple root nodes) from a flat student list by parsing each student's parent-reference field (format `"ID_姓名"` via `parseNameWithId()`), and — critically — it already has cycle detection built in: a DFS (`resolveNode`) tracks an `inPath` set, and when it revisits a node already in the current path, it deletes that node's parent link (`parentMap.delete(node)`), which turns that node into a new root instead of recursing forever. This is exactly the protection this change needs for `little_angel` chains, and reusing it is far lower-risk than writing new tree/cycle logic from scratch.

2. **Verified against real data**: querying the full `students` table and running `little_angel` through the same algorithm confirms it handles both circular cases found in the data correctly without hanging — self-reference (`id=27920`'s `little_angel` points to itself) and mutual reference (`id=13804` ↔ `id=23546` point to each other). See Decisions below for exactly how each is handled, because they go through **different code paths** with different implications for the data-quality reporting requirement.

3. **`spirit-ambassador-hub`'s page (`app/spirit/page.tsx` + `SpiritClient.tsx`)** is the direct structural template: Server Component fetches all in-system students with `applySystemFilter`, computes KPIs/chart data in plain JS, passes plain data down to a Client Component that renders `recharts` bar charts plus a data-quality section. This change follows the same shape.

## Goals / Non-Goals

**Goals:**
- Reuse `buildTree()` for the little-angel hierarchy by generalizing its hardcoded `introducer` field access into a parameter, without changing its behavior for existing `introducer`-based callers (`OrgChart`, `RelationshipNetwork`).
- Surface both kinds of circular `little_angel` data (self-reference, mutual reference) in the data-quality section, even though only one of them naturally shows up in `buildTree()`'s own cycle-breaking output (see Decisions — this needs an explicit additional check).
- Surface "points to a non-existent student ID" as a separate, common data-quality case (verified: 11 out of 11 sampled "chain" cases in the real data turned out to be this, not genuine multi-level chains — see Decisions).
- Ship KPIs, a ranking bar chart, an expandable tree view, a system/geography distribution view, and the data-quality section, matching `spirit-ambassador-hub`'s established page shape.

**Non-Goals:**
- Not changing how `little_angel` or `role` are imported, stored, validated at write time, or displayed/filtered in the existing grid — this is a new read-only view, not a data-model change.
- Not building a generic "any field" relationship-tree UI — the tree view is specific to `little_angel`; if a future need arises for other fields, `buildTree()`'s new field parameter makes that easy to add later, but this change doesn't build a field-picker UI for it.
- Not attempting to auto-repair bad data (self-references, mutual references, dangling pointers) — the data-quality section only surfaces these for manual correction, matching how `spirit-ambassador-hub`'s data-quality section works today (list, don't fix).
- Not adding a new "little angel" role-based view (i.e., not building a second section for `role = '小天使'` people) — explicitly descoped per the user's decision to focus on the `little_angel` field relationship, not the role field.

## Decisions

**1. Generalize `buildTree()` to accept a `parentField` parameter instead of hardcoding `introducer`.**
Change the signature to `buildTree(students, parentField: keyof OrgStudent, aliases?, overrides?)` (or equivalent), and have every place that currently calls `student.introducer` internally read `student[parentField]` instead. `OrgStudent` already doesn't declare `little_angel`, so it needs to be added to that interface (as `string | null`, matching every other optional field there).
- Verified this doesn't break existing behavior: the only two current callers (`OrgChart`, `RelationshipNetwork` via `useOrgData`) always pass data that has `introducer` populated the same way; adding a required parameter with an explicit value at each call site (`'introducer'`) keeps their behavior identical, it's a pure refactor for them.
- Alternative considered: copy `buildTree()` into a new `buildLittleAngelTree()` function instead of generalizing. Rejected — this would duplicate ~90 lines including the cycle-detection logic, meaning any future bugfix to cycle handling has to be applied twice; the field-parameterization is a small, mechanical change that keeps a single source of truth for tree-building + cycle protection.

**2. Self-reference and mutual-reference cycles are NOT equivalent from `buildTree()`'s perspective — data-quality reporting needs an explicit self-reference check outside of `buildTree()`'s own cycle output.**
Verified directly: `buildTree()` (unmodified) has an early guard `if (parent && parent !== node)` before ever recording a parent link — so a self-reference (`little_angel` resolves to the student's own ID) never even enters `parentMap`, and therefore never triggers the DFS cycle-detection path (`resolveNode`'s `inPath` check) or gets added to what would be a "broken cycles" list. A mutual reference (A→B→A) *does* go through the DFS path and gets caught there (one of the two nodes has its parent link deleted and becomes a root). Practically: if the data-quality section only reported whatever `buildTree()`'s cycle-breaking touched, self-references would be silently invisible to the user — this was confirmed by directly testing both cases against the real `id=27920` (self) and `id=13804`/`id=23546` (mutual) records.
- **Resulting requirement for whoever implements this**: compute the self-reference list *before* calling `buildTree()`, via a simple separate pass — `students.filter(s => parseNameWithId(s.little_angel).id === s.id)` — and merge that into the data-quality section alongside whatever cycle information `buildTree()` surfaces (if `buildTree()` is extended to return broken-cycle info at all; see Decision 3). Don't rely on `buildTree()`'s return value alone to catch self-references.

**3. `buildTree()` currently returns only `TreeNode[]` (the roots) — it does NOT currently expose which nodes had their cycle-causing parent link broken.**
Looking at the current implementation, `parentMap.delete(node)` inside `resolveNode` discards the broken link silently; the function has no return channel for "these node IDs had a cycle broken." To satisfy the data-quality requirement ("列出循環引用...供人工核對修正"), this change needs `buildTree()` to optionally return that list (e.g. add a `brokenCycleIds: number[]` to a richer return type, or accept an optional out-param/callback) — a small, additive change to the function's return shape.
- Alternative considered: leave `buildTree()` untouched and re-derive cycle info by walking the raw data separately (e.g. detect A→B→A patterns with a manual pass). Rejected — that duplicates cycle-detection logic a second time (for reporting) that already exists once (for tree-building), risking the two falling out of sync; extending the one existing implementation to also report what it broke is more consistent and less code overall.

**4. "Dangling pointer" (`little_angel` parses to an ID that doesn't exist in the current dataset) is the dominant real-world data-quality case, not deep multi-level chains.**
Verified: of 11 "little angels who themselves have a `little_angel` filled in" sampled directly from the database, **all 11** pointed to an ID with no matching student record (`parseNameWithId(...).id` doesn't resolve via `nodeById.get(...)`) — this is what `buildTree()`'s existing fallback-to-name-lookup already partially handles (falls back to matching by bare name if ID lookup fails), but if that also fails, the student simply becomes a root with no parent, silently. This has UX implications: **most people who look like they might have deep chains, on this dataset, actually don't — they're broken references that should be surfaced, not tree depth to celebrate.** The tree view's "多層" scenario in the spec is real (this data structurally supports it) but will likely render as shallow trees in practice until the dangling-pointer data-quality items get fixed by counselors.
- This is exactly why the data-quality section is not optional polish here — without it, the tree view alone would understate a real, sizeable data problem (161 people are recorded as "someone's little angel," but the chain-depth signal is mostly noise from bad IDs, not real hierarchy).

**5. Ranking, KPIs, and geography/system distribution are computed once in the Server Component (`page.tsx`), passed as plain serializable data to the Client Component** — same division of responsibility as `spirit-ambassador-hub`.
- `county`-based distribution (added recently in a separate change) buckets by the raw `county` string value; empty/null `county` buckets into an explicit "未填寫" category rather than being dropped, per the spec.
- System distribution: since this page already scopes all data to `getEffectiveSystem(user)` per the existing tenant-isolation pattern, a superadmin viewing "星光" sees only 星光 data — there's no cross-system toggle inside the page; switching system means switching the existing system-selector cookie, same as every other page. The "體系分布" chart scenario in the spec, in practice, mostly matters for a superadmin comparing systems by switching between them, not a single split-screen view — consistent with how `spirit-ambassador-hub` and the rest of the app already handle multi-system comparison (switch, don't split).

**6. Navigation links added to five existing files**, matching how `spirit-ambassador-hub` was wired in: `app/dashboard/DashboardClient.tsx`, `app/students/StudentsClient.tsx`, `components/MaintenanceLayout/index.tsx`, `components/CounselorsLayout/index.tsx`, and `app/spirit/SpiritClient.tsx` (each gets a new `NavButton` pointing to `/little-angel`); the new page itself gets return links to those five in the same style `SpiritClient.tsx` already uses.

## Risks / Trade-offs

- [Risk] Generalizing `buildTree()`'s signature is a breaking change to its call sites (`OrgChart`/`RelationshipNetwork` via `useOrgData`) if the new parameter isn't threaded through correctly → Mitigation: make the new parameter required (not optional with a default), so `tsc` will fail loudly at every existing call site until it's updated — a missed call site can't silently keep working with the wrong field.
- [Risk] Extending `buildTree()`'s return shape (Decision 3) to include broken-cycle info changes its type signature, another point where existing callers need updating → Mitigation: same as above — TypeScript will catch every place that destructures the old shape; existing callers that only use the roots array can ignore the added field without needing behavior changes.
- [Risk] Self-reference detection (Decision 2) requires a second, separate pass over the data outside of `buildTree()` — a future maintainer might reasonably assume `buildTree()`'s cycle output is exhaustive and forget this gap → Mitigation: document this explicitly at the call site in `little-angel` page code (not just in this design doc) so the two-pass requirement is visible in the code itself, not just in change history.
- [Risk] Dangling-pointer detection (Decision 4) requires checking every `little_angel` value against the full in-system student ID set — for ~2800 students this is a cheap `Set` lookup, not a real performance concern, but worth naming since it's an additional full pass beyond what `buildTree()` itself does.
- [Risk] The tree view's real-world usefulness is limited by how much dangling/bad data exists today (Decision 4) — this is a data quality problem, not a code defect, and the data-quality section is the intended remedy path (surface it, let counselors fix the source data), not something this change can code its way out of.

## Migration Plan

No database schema changes — this change is entirely new read-only code (one new page, one new client component, a small generalization of an existing shared utility). No migration to run, no rollback complexity: reverting the code change fully removes the feature with no lingering state.
