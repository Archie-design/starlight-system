## Context

See proposal.md - Why for motivation. This follows the same established page shape as `app/spirit/page.tsx` and `app/little-angel/page.tsx`: a Server Component fetches all in-system students (paged, `applySystemFilter` + `getEffectiveSystem`), computes aggregates in plain JS, and passes serializable data down to a Client Component that renders `recharts` charts plus interactive drill-down UI.

Two existing utilities this reuses directly:
- `lib/utils/courseUtils.ts`'s `parseCourseValue(value)` — parses a stored course string like `"1-88-正取"` into `{ level, batch, status }`, or `{ level: null, batch: null, status: value }` for non-batch values like `"待確認梯次"`. Verified against live data: `course_1` alone has 67 distinct batches across 2738 enrolled students, confirming batch-level analysis is meaningful (not sparse/trivial).
- The "owes money" numeric check currently lives as a private, unexported `NUMERIC = /^\d+(\.\d+)?$/` regex inside `lib/utils/studentStatus.ts`, used internally by `owesPayment()`. This change needs the same definition to compute per-batch/per-stage owed amounts (not just a boolean "owes or not" — the proposal explicitly asked for actual summed amounts), which `owesPayment()` itself doesn't expose (it only returns a boolean for the *whole student*, not per-field amounts).

Verified data shape for scope decisions:
- `course_1` through `course_5`: enrollment counts step down as expected (2738 → 1866 → 1036 → 664 → 591), each with a healthy spread of distinct batches (67, 41, 21, 16, 16 respectively) — batch-level charts will have real, non-trivial data to show at every stage.
- `course_wuyun`: all 640 non-null values are the literal string `"五運"` — `parseCourseValue()` on this returns `{ level: null, batch: null, status: "五運" }` (no digit-dash-digit pattern to match), confirming there is no batch structure to analyze; only enrollment/payment counts make sense here, per the user's explicit scoping decision.
- The four "special courses" (`life_numbers`, `life_numbers_advanced`, `life_transform`, `debt_release`) are simple non-null/null flags with no paired payment field — structurally different from the six fields this hub covers, and explicitly out of scope per the user's decision.

## Goals / Non-Goals

**Goals:**
- Batch-level (梯次) enrollment distribution for course_1 through course_5, reusing `parseCourseValue()`.
- Owed-amount totals (not just counts) per stage and per batch, computed with the same numeric-string definition `owesPayment()` already uses internally.
- Drill-down: select a stage or a specific batch → see the matching student roster, linking out to `/students`, matching the interaction pattern already established by `spirit-ambassador-hub` (click a group bar → member list) and `little-angel-hub` (click a ranking bar / search → tree modal).
- Course_wuyun included for payment stats only, no batch breakdown.

**Non-Goals:**
- Not touching `/dashboard`'s existing course-related charts (course funnel, payment distribution) — those stay as the system-wide summary view; this hub is an additional, deeper view, not a replacement.
- Not including the four special courses (`life_numbers`/`life_numbers_advanced`/`life_transform`/`debt_release`) — explicitly descoped by the user; their data shape (flag-only, no payment pairing) doesn't fit this hub's "enrollment + payment" theme anyway.
- Not building a "待確認梯次" (unscheduled) tracking/alert feature — the user explicitly did not select this option when scoping the hub; those students still count toward each stage's total enrollment count, but get no dedicated attention section (unlike, say, `spirit-ambassador-hub`'s data-quality alerts, which *were* explicitly requested there).
- **Superseded during implementation**: this originally read "Not adding new database columns, migrations, or changes to the import/export pipeline." The user requested makeup-class completion tracking and club (聯誼會) registration stats after seeing the first rendered version — both required source data (18 makeup-class attendance columns, 2 club columns) that had never been imported at all. Kept here as a record of the original scope boundary; see the new "Makeup-class and club data" section below for what was actually added and why the boundary moved.

### Makeup-class and club data (added post-implementation, per user feedback)

**Why this wasn't pure aggregation after all**: verified against the sample file that `students` had zero columns for the 18 "一階課程 - 同學會" etc. headers, and zero for "聯誼會加入日"/"聯誼會組別" (the existing `membership_expiry` column maps to "聯誼會籍", i.e. membership expiry date, not registration status — a different concept). Showing this data in the hub required extending the import pipeline first, not just aggregating what was already there.

**Decisions**:
- New columns named `l{level}_makeup_{seq}` (e.g. `l1_makeup_1`..`l1_makeup_6`) rather than a name derived from each class's Chinese title — titles are free text that could plausibly be edited in a future source file revision, while the position-based sequence within a stage is stable. Each column's corresponding Chinese class title is kept in application code (`MAKEUP_CLASSES` in `page.tsx`) instead of being baked into the column name.
- Column values are stored as the raw "class date/time" text (e.g. `"2026/08/19 (三) 19:00"`), matching the existing `course_N`/`wuyun_a`..`wuyun_f` convention where "has a value" means "attended" — not normalized to a date type, since the source format includes a Chinese weekday and isn't a clean parseable date.
- `club_join_date` (DATE column) determines "registered" the same way `spirit_ambassador_join_date` already determines "is a 心之使者" — presence of a value means yes. `club_group` is free text, stored but not required to be non-null.
- Completion rate per class is computed against a stage-specific denominator: "已上該階主課者" (`course_N` is non-null), not the full student population — a student who hasn't taken the main course yet can't meaningfully be "behind" on that stage's makeup classes.
- Attendance and absence rosters for each makeup class are pre-built server-side (`roster[\`makeup-${level}-${idx}\`]` and the `-absent` suffix variant) rather than computed client-side from a larger payload, consistent with how batch/stage rosters were already being built in this same file.

**Verified**: import parsing tested against the real sample file (`學員資料庫 20260826 (1).xlsx`) — all 2096 rows parsed successfully, spot-checked makeup-class and club values against the source spreadsheet. End-to-end verification of the computed completion rates against the live database is pending — it requires migration 018 to be applied first (user will run it separately).

### Aggregate incomplete roster, l2/club gap roster, and CSV export (added post-implementation, per user feedback after migration 018 was applied and real data populated)

**Why**: after seeing the rendered completion-rate cards with real data, the user pointed out two gaps: (1) the per-class attendance/absence rosters already existed, but there was no single "hasn't finished everything yet" roster to work from when following up with students who need encouragement — a counselor would have to check each class's absent list separately and cross-reference. (2) There was no way to see who's already completed 二階 but hasn't registered for 聯誼會 (the club) — a natural recruitment target list that didn't exist anywhere. Both needed to be viewable *and* exportable, and the user extended the export requirement to every existing roster modal in the hub, not just the two new ones.

**Decisions**:
- **Incomplete roster is a distinct "overall view" list, not a UI aggregation of existing per-class absent rosters.** Computed server-side in the same per-stage loop that builds the per-class attendance/absence rosters (`app/courses/page.tsx`), stored under `roster[\`incomplete-makeup-${level}\`]`. A student appears here iff they've taken the stage's main course and have NOT attended every one of that stage's makeup classes. Each entry's `statusLabel` is `已上 X / Y 堂` (attended count / total count for that stage) so counselors can sort by how far behind someone is — this is the piece of information a per-class absent list can't give at a glance (a student on one class's absent list might have already attended all the others).
- **"已完課" for the 二階/聯誼會 intersection uses `parseCourseValue(course_2)?.status === '已上課'`, not `course_2 != null`.** Confirmed explicitly with the user before implementing: the looser "has any course_2 value" check would include students who are 正取/候補/待確認梯次/中離 — i.e. haven't actually attended level 2 yet — which would make the resulting "invite to club" list actively misleading. Verified against live data: `course_2` status distribution is 已上課=1242, 待確認梯次=293, 正取=278, 候補=49, 中離=3 — the strict filter meaningfully excludes ~25% of nominally-enrolled students who haven't actually completed the course.
- **Scoped to 二階 only, not generalized to all 5 stages.** The user's request specifically named 二階/聯誼會; generalizing to "completed stage N but not registered for [some related program]" isn't a pattern that exists for the other stages (there's no equivalent "club" concept per stage), so a `L2ClubGap`-shaped one-off (rather than a parameterized `MAIN_STAGES`-style loop) matches the actual scope and avoids speculative generality.
- **CSV export is client-side only (`Blob` + `URL.createObjectURL` + synthetic `<a download>` click in `CourseClient.tsx`), not a new `/api/*` route.** Roster modals hold at most a few hundred rows already resident in the page's props (not re-fetched), so there's no server round-trip to justify — this differs from `/api/export`'s server-streamed xlsx, which handles the full student database and needs `exceljs` to build a real workbook. Reusing that pipeline for a already-in-memory list of ≤~2800 rows would be pure overhead. CSV (not xlsx) was the user's explicit choice, matching the "small, already-loaded list" use case.
- **The export button lives once in the shared roster Modal component, not per-roster-type.** Every `roster[key]` entry is already shaped as `RosterStudent[]` (`{ id, name, statusLabel, paymentLabel, owes }`) regardless of which roster it is — batch, stage-total, wuyun, makeup-class attended/absent, the new incomplete roster, club-joined, or the new l2-club-gap roster all use the same shape. A single `downloadRosterCsv(title, rows)` call in the modal header, using `rosterTitle` (already computed via `useMemo` from `rosterKey`) as both the CSV filename and it being non-empty as the natural signal that a roster is open, satisfies "add an export button to every roster modal" without per-roster-type code. The button is disabled when the currently-open roster list is empty.
- **CSV columns are name/status/note (姓名/狀態/備註) — a fixed 3-column shape across all roster types**, not a per-roster-type column set. `RosterStudent`'s `statusLabel` and `paymentLabel` fields already carry whatever's meaningful for that roster (e.g. "已上 X / Y 堂" for the incomplete roster, "二階已完課"/"未報名聯誼會" for the l2-club-gap roster, batch/payment status for stage rosters) — reusing them directly as CSV columns avoids a per-roster-type export schema while still producing a meaningful export for each roster type.
- UTF-8 BOM (`﻿`) prefix on the CSV content, matching the concern (Excel mojibake on Chinese text without it) already implicit in how the rest of the app treats Chinese-text exports (`lib/export/buildXlsx.ts` doesn't need this since xlsx isn't plain text, but the equivalent concern for a plain-text CSV export is well-known and worth guarding against explicitly).

**Verified**: internal consistency checked against the live database (post-migration-018, real imported data) for all 5 stages — `fullyAttendedMakeupCount + incompleteMakeupCount === completedMainCourseCount` holds exactly in every case (1: 75+2678=2753, 2: 93+1772=1865, 3: 105+932=1037, 4: 76+587=663, 5: 138+453=591). `course_2` status breakdown (above) confirms the strict "已上課" filter behaves as intended; sampled several individual students from the resulting l2-club-gap roster and confirmed their raw `course_2`/`club_join_date` values match expectations. CSV escaping (comma/quote/newline handling, BOM prefix) verified in isolation against representative inputs including Chinese text and special characters.

### CSV export contact columns (added post-implementation, per user feedback after seeing the CSV in real use)

**Why**: after the CSV export shipped, the user pointed out that these exports exist specifically so 關懷員 (care coordinators) can follow up with the listed students — a name-only export doesn't let anyone actually reach out. `RosterStudent` needed `phone` and `line_id` (the two contact fields already on `students`, per `lib/supabase/types.ts`) added to its shape, and the CSV needed to expose them alongside the existing `id`.

**Decisions**:
- **Extended `RosterStudent` itself (`id`, `phone`, `lineId` on every entry) rather than fetching contact info separately at export time.** Every one of the six `roster[...]` construction sites in `app/courses/page.tsx` already has the full student row in scope when building each entry — passing `phone`/`line_id` through costs nothing extra there, and keeps the CSV export function itself simple (just read fields off the object it already has), instead of doing a second lookup keyed by id right before download.
- **CSV column order is ID, 姓名, 手機, LINE ID, 狀態, 備註** — identity/contact columns first (what a 關懷員 needs to actually place the call or send the LINE message), the roster-specific status/note columns last. `id` was added even though it wasn't in the original 3-column CSV — useful as a stable join key if the export is cross-referenced against another export later (e.g. `/api/export`'s full student database), and it was already on every `RosterStudent` as the roster-modal-link key, so exposing it in the CSV was free.
- **Missing phone/line_id render as an empty CSV field, not a placeholder like "—".** The in-app roster list UI uses "—" for missing payment values (a display convention for a screen a person reads directly), but a CSV is typically consumed by re-importing into a spreadsheet or another tool — a placeholder string there is noise, not signal, so empty-string is the correct "no data" representation for a machine-consumable format.
- **The UI roster list itself was not changed to show phone/line_id inline** — modal width is already tight (a single name + status + payment-label row), and clicking a student already links to `/students` where full contact info is visible. Adding two more columns to a scannable roster list for what is fundamentally an "export to go make calls" workflow didn't pull its weight; the CSV is the actual deliverable for that workflow.

**Verified**: queried a live sample of the l2-club-gap roster (435 students in a 1000-row sample) — 433 had a phone number, 425 had a LINE ID, 423 had both, 0 had neither, confirming the added columns will be populated for the overwhelming majority of real export rows. CSV output re-verified in isolation with the new 6-column shape (ID/姓名/手機/LINE ID/狀態/備註), including a row with a null LINE ID rendering as an empty field.

### Roster modal: table layout with filter and sort (added post-implementation, per user feedback after seeing the modal in real use with real data)

**Why**: the modal was a single-column card list — fine for name + one status glance, but once phone/line_id were added (previous addition) there was nowhere natural to show them, and with real rosters running into the thousands (e.g. "一階・未全部完課" at 1963 people, per the screenshot) a flat unsorted, unfilterable list is unusable for actually working through it.

**Decisions**:
- **Modal widened from `max-w-sm` to `max-w-3xl`** to fit a 5-column table (姓名/手機/LINE ID/狀態/備註) without cramming — the prior width was sized for a single name+status+payment row, not a table.
- **Table columns are name/phone/line_id/status/note — the same five fields already on `RosterStudent`**, no new data shape. Name stays a link to `/students?search=...` (unchanged behavior, per user's explicit confirmation to keep it) rather than making the whole row clickable, so row-level interactions (future row selection, etc.) aren't blocked by an accidental full-row link.
- **Sortable columns: name, status, note — not phone/line_id.** Per user's explicit choice. Clicking a column header toggles asc/desc (same header clicked twice reverses direction); an arrow indicator (▲/▼) shows the active sort column and direction, dimmed (▲, non-color) on inactive columns as an affordance hint that they're clickable too.
- **Status-column sort is numeric-aware for the "已上 X / Y 堂" format** (used by the incomplete-makeup roster) — extracts X via regex and sorts numerically, falling back to plain string comparison (`localeCompare` with `'zh-Hant'`) for every other roster's status format (attendance timestamps, "已上課", batch/payment labels, etc.). Without this, "已上 10 / 6 堂"-style labels would sort lexicographically (10 before 2) wherever a stage has ≥10 makeup classes worth of range in the numerator — not currently possible given the actual per-stage class counts (max 6), but the numeric-aware comparator was cheap to add and removes a footgun if a stage's makeup-class count ever grows.
- **Filtering: one free-text search box (matches name/status/note/phone/line_id, case-insensitive substring) plus a status dropdown**, per user's explicit choice of scope — a per-roster-type "status enum" filter was considered and rejected in favor of building the dropdown's options dynamically from `Array.from(new Set(rosterListRaw.map(m => m.statusLabel)))` for whichever roster is currently open, since status-label shapes vary wildly across roster types (plain status string, attendance date-time text, "已上 X / Y 堂") and a hardcoded option set couldn't cover all of them. The dropdown is hidden when a roster has ≤1 distinct status value (e.g. every entry in an absent-roster already shares "未出席") since it wouldn't filter anything.
- **Filter/sort state resets on every `openRoster()` call** (a new wrapper around the existing `setRosterKey` that also clears search/status-filter/sort back to defaults) rather than persisting across roster switches — carrying over a search term or sort from the previous roster silently applied to an unrelated roster would look like a bug ("why is my filter empty" / "why did my search disappear the results").
- **CSV export continues to export the currently filtered+sorted `rosterList`, not the raw unfiltered roster`rosterListRaw`** — this was already true before this addition (export always read whatever `rosterList` was), and stays true now that `rosterList` itself is filter/sort-aware; the modal header shows "filtered / total" counts (e.g. "42 / 1963 人") so it's visually clear the export will reflect the current filter, not the full roster.

**Verified**: `npx tsc --noEmit` clean. Sort comparator tested in isolation against a mixed "已上 X / 6 堂" sample (0/3/5/10) confirming numeric order (0,3,5,10) rather than lexicographic (0,10,3,5) in both directions, and against a non-numeric status format (attendance date-time strings) confirming it falls back to `localeCompare` correctly.

### Excluding a discontinued makeup class from completion stats (added post-implementation, per user feedback: "上級貴人成功學" is no longer offered)

**Why**: 一階's "上級貴人成功學" class has stopped being held. Counting it in the 6-class completion denominator was penalizing every student who otherwise finished everything — their "未全部完課" status was really "waiting on a class that no longer runs," which is not a meaningful thing to ask them to complete.

**Decision — remove the entry from `MAKEUP_CLASSES[1]` in `app/courses/page.tsx`, leave everything else untouched.** Explicitly confirmed with the user: keep the `l1_makeup_5` column, its import mapping (`HEADER_TO_COL_KEY`), `COMPARABLE_FIELDS` diff entry, and all historical attendance data in the database exactly as-is — only stop counting this class in the completion-rate computation. `MAKEUP_CLASSES` is the single source driving both the per-class attendance cards and the `fullyAttendedMakeupCount`/`incompleteMakeupCount` aggregate — removing this one array entry automatically drops the stage's statistical denominator from 6 to 5 classes everywhere that reads `classes.length`, with no other code change needed.
- **Alternative considered and rejected**: dropping the column via a new migration. Rejected per explicit user instruction — this would destroy 554 real students' historical attendance records for a class that *did* happen for them at the time, which is a materially different (and much larger, irreversible) change than "stop counting it going forward." The chosen approach is also trivially reversible: if the class resumes, adding the array entry back requires no migration or data repair.
- **Roster keys for makeup classes (`makeup-{level}-{idx}`) are safe to shift.** These keys are array-index-based into `MAKEUP_CLASSES[level]`, but both the key and the `roster[key]` data it addresses are recomputed together on every server render from the same (now 5-entry) array — there's no persisted/cached key from a prior render that could point at the wrong class after the array shrinks. No client-visible breakage from the index shift.

**Verified**: live query against the real database — 一階 enrolled = 2753 in both cases; with the 6-class denominator, fully-attended = 75 / incomplete = 2678; with the corrected 5-class denominator (上級貴人成功學 excluded), fully-attended = 128 / incomplete = 2625 — both sums equal 2753 as expected, and the fully-attended count rose (as expected: everyone who was only missing this one discontinued class now correctly counts as complete). Confirmed 554 students' historical `l1_makeup_5` attendance values remain untouched in the database, simply no longer read by the completion-rate computation.

### 一階解圓夢計劃資格名單 (added post-implementation, per user feedback: a new eligibility rule — 一階 graduates who've also attended 3+ non-reunion makeup classes qualify for "解圓夢計劃")

**Why**: a business rule exists granting "解圓夢計劃" (dream-realization program) eligibility to students who've completed 一階's main course and additionally attended at least 3 of 一階's makeup classes (excluding 同學會/reunion sessions). There was no way to see who currently qualifies — this is a distinct question from "課後課完課狀況" (which tracks full completion of *all* makeup classes): this rule has a lower, fixed numeric threshold (3, not "all"), and explicitly excludes one specific class (同學會) that the completion-rate feature does count.

**Decisions**:
- **"一階已完課" uses `parseCourseValue(course_1)?.status === '已上課'`** — the same strict definition already established for the l2-club-gap query (confirmed with user), for the same reason: 正取/候補/待確認梯次/中離 students haven't actually finished the course yet and shouldn't count toward eligibility.
- **同學會 exclusion is an explicit `isReunion?: boolean` flag on each `MAKEUP_CLASSES` entry, not a `label === '同學會'` string match.** Every stage's makeup-class list happens to have "同學會" as its first entry, but matching on the label string would silently break if that class's title were ever edited (labels are free text sourced from the spreadsheet's column headers, not stable identifiers — see the existing `l{level}_makeup_{seq}` column-naming decision in this same file). The explicit flag is checked once when building `l1NonReunionClasses`, decoupled from the display label entirely.
- **Threshold (3) is scoped to 一階's own non-reunion makeup classes only, not summed across stages.** Confirmed with user: this rule is specifically about 一階 graduates, and after excluding 同學會 and the already-discontinued 上級貴人成功學 (see the section above), 一階 actually has only 4 eligible classes (我喜歡/討厭自己的原因、上平下緣傳愛道、對好心沒好報的誤解、金錢的助流) — so "3 or more" means attending at least 3 of these 4.
- **The threshold value (3) is passed down through `L1DreamProgram.threshold` rather than duplicated as a separate constant in `CourseClient.tsx`.** The subtitle text ("另上完 N 堂以上...") needs the number, and hardcoding it a second time client-side would create exactly the kind of drift risk this codebase's own review history has flagged before (see the `NUMERIC` export decision above) — one `DREAM_PROGRAM_THRESHOLD` constant in `page.tsx` is the single source, both the roster-membership computation and the displayed threshold text read from it.
- **Roster entry `statusLabel` is "已上 X 堂（不含同學會）"** (X = count of attended non-reunion 一階 makeup classes), mirroring the existing "已上 X / Y 堂" convention from the incomplete-makeup roster but without the "/ Y" denominator — there's no fixed total being tracked toward here (attending all 4 doesn't grant "more" eligibility than attending exactly 3), so showing a fixed threshold as if it were a required total would be misleading.
- **No new UI pattern**: a single Card with a roster-opening button (same shape as the l2-club-gap card added earlier), and the roster it opens automatically gets the shared table/filter/sort/CSV-export modal from the "roster modal: table layout" addition (no roster-type-specific work needed there) — this was the point of building that feature as roster-shape-agnostic in the first place.

**Verified**: live query — 一階已完課 (course_1 精確為「已上課」) = 2169 people. Distribution of attended non-reunion-class counts among them: {0: 1144, 1: 252, 2: 242, 3: 371, 4: 160}, summing to 2169 (internally consistent). Qualified (≥3) = 371 + 160 = 531, matching the code's computed `qualifiedCount`. Spot-checked 5 individual qualified students' raw `l1_makeup_2`/`l1_makeup_3`/`l1_makeup_4`/`l1_makeup_6` values against their reported attended counts.

## Decisions

**1. Export `NUMERIC` from `lib/utils/studentStatus.ts` (or an equivalent shared definition) rather than duplicating the regex in a new file.**
The "is this payment value a still-owed amount" check must stay in exactly one place — `owesPayment()`'s per-student boolean logic and this hub's per-batch/per-stage amount-summing logic need to agree on what counts as "owed" (a bare numeric string) or the two views of the same data could silently disagree (e.g. dashboard says student X owes money, course hub's stage total doesn't include them, or vice versa). Renaming the constant to `export const NUMERIC_PAYMENT = /^\d+(\.\d+)?$/` (or exporting the existing name) and importing it from the new aggregation code keeps a single source of truth.
- Alternative considered: copy the regex literal into the new course-hub code. Rejected — this is exactly the kind of small duplicated business rule that drifts silently over time (the codebase's own review history already flagged this pattern as a recurring risk elsewhere — see the parallel-whitelist case for filterable columns).

**2. Compute owed amounts by parsing `payment_N` as a number when it matches the numeric-string pattern, summing per stage and per batch — payment amount is NOT a separate stored field, it *is* the payment string itself when numeric** (per `lib/import/transform.ts`'s `buildPaymentValue()`: a numeric payment value already means "this is the remaining balance owed", not "this is some other amount that happens to look numeric").
No new parsing logic needed beyond `Number(paymentValue)` after the `NUMERIC` regex test — this mirrors `buildPaymentValue()`'s own inverse operation (the import pipeline already treats a numeric string in this field as literally the owed balance).

**3. Batch key for grouping is `${level}-${batch}` from `parseCourseValue()`'s output** (matching the existing `cohortKey()` convention in `lib/utils/relations.ts`, which already builds this exact key format for its own "same cohort" relationship feature) — reusing an established key format rather than inventing a new one.

**4. Drill-down UI: a stage selector (tabs or buttons for 一階~五運) plus, within a selected stage, a clickable batch bar chart; clicking either level opens a roster panel** (modal, matching `spirit-ambassador-hub`'s and `little-angel-hub`'s existing modal-on-click pattern) **listing students with name, batch/status, and payment status, each linking to `/students?search=...`** (identical link pattern already used by both existing hubs' roster items).
- Alternative considered: a single mega-chart with all five stages stacked. Rejected — batch counts vary wildly by stage (67 batches for 一階 vs 16 for 四/五階), a single combined chart would either be unreadable at 一階's scale or waste space at 五階's scale; a per-stage selector keeps each chart's scale appropriate to its own data.

**5. System scoping and navigation wiring follow the exact same pattern as `little-angel-hub`**: Server Component computes everything scoped to `getEffectiveSystem(user)`, superadmin gets a system-switch control that sets the `sl_view_system` cookie and calls `router.refresh()`, and the same six existing hub-style pages (dashboard, students, maintenance, counselors, spirit, little-angel) each gain one more nav link — no new navigation pattern introduced, this is now the sixth page following that convention.

## Risks / Trade-offs

- [Risk] Renaming/exporting the private `NUMERIC` constant in `studentStatus.ts` touches a file used by several existing features (`owesPayment()`, `membershipStatus()` lives in the same file) → Mitigation: this is an additive export, not a behavior change to any existing function — `owesPayment()`'s own logic is untouched, only its previously-private regex becomes importable elsewhere; `npx tsc --noEmit` will catch any accidental signature change.
- [Risk] Owed-amount totals could be misread as "money actually collectible" when in practice some of these balances may already be in dispute, written off, or otherwise not simply collectible — this is a display/labeling concern, not a computation risk → Mitigation: label the figure clearly as "帳面欠款金額" (book-value owed amount) or similar in the UI, consistent with how the rest of the app already treats payment fields as raw recorded values rather than a settled ledger.
- [Risk] A stage with very high batch cardinality (67 for 一階) rendered as a horizontal bar chart could get visually crowded → Mitigation: same scrollable-container-with-height-cap pattern already used by `spirit-ambassador-hub`'s "各組人數" chart and `little-angel-hub`'s ranking chart (fixed max-height, internal scroll, `Math.min(Math.max(count * rowHeight, min), max)` height calculation) — no new pattern needed, directly reuse the existing one.

## Migration Plan

No database schema changes — this is entirely new read-only code (one new page, one new client component, one additive export from an existing utility file). No migration to run, no rollback complexity: reverting the code change fully removes the feature with no lingering state.
